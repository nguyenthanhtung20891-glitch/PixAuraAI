## Existing execution envelope

CPU, Android Vulkan and Apple Metal execute only the frozen
`pixaura.onnx.reference-segmentation.v1` profile: IR 9/opset 13, one attribute-free
1x1 Conv, no bias, three quarter-step nonnegative weights summing to one.
It cannot distinguish identically colored pixels using spatial/subject context.
This is an execution-contract fixture, not a production foreground model.
No model download, raw-path execution or provider-profile expansion is proposed.

U2NETP's source requires spatial/dilated/bias Conv, BatchNormalization, Relu,
MaxPool, bilinear upsampling, Concat, residual Add and Sigmoid. None of this
multi-node topology is executable by the frozen single-Conv profile. These are
source-level requirements; an exact exported ONNX operator inventory/opset,
folding choices and artifact digest remain unknown until approved conversion.
Stock model returns seven outputs, whereas the contract accepts one. Its stock
preprocessing uses mean/std offsets and image-dependent scaling, unlike the
frozen range-preserving normalization. Stock prediction min/max rescaling is
also different from the runtime probability contract; it must not be copied
silently. Model suitability is inferred from its saliency task and spatial
architecture, not from unperformed quality tests. Saliency is not guaranteed
user-intended subject selection, and binary segmentation is not alpha matting.

## Product and platform implications

Meaningful U2NETP execution requires reviewed model conversion/preprocessing,
CPU runtime or substantial owned operator work, Android/Apple implementations
and new parity/resource certification. Neither accelerator is implicitly capable
because it supports Conv. No credible latency, peak memory, model ranking or
quality score is available without executing approved artifacts/data. Package
size alone cannot estimate intermediate activations or mobile performance.

The current providers therefore cannot execute this plausible compact candidate.
This is an evaluation finding, not a failing existing provider implementation.
No production threshold or production candidate is selected.

## Architecture decision and future options

1. **Option A, APPROVED:** finish Step 5 as a bounded model-agnostic metric and
   synthetic evaluation framework using existing verified reference fixtures and
   trivial baselines only. Record useful models as unsupported and production
   selection unresolved. No provider, package, normalization or runtime expansion.
   This matches the explicitly allowed negative feasibility conclusion.
2. **Option B:** separately authorize a specifically frozen broader model/profile
   and owned CPU/Android/Apple operators. Highest implementation/security/parity
   cost; must preserve the existing reference profile and review preprocessing.
3. **Option C:** separately audit/select a pinned general local runtime and
   approved model artifact. Less interpreter development, but new dependency,
   license, binary-size, ABI and provider-certification decisions. No runtime is
   selected or incorporated by this review.
