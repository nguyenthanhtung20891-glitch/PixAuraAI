# Image document and edit pipeline contract, version 1

Status: frozen Phase 2 Step 1 document design, with user-approved Step 2 context clarification, 2026-10-03. ADR [0008](../adr/0008-document-stacks-and-manifest.md) refines ADRs 0001-0004; [0009](../adr/0009-explicit-document-context.md) supersedes only the context-free registry design. Step 2 implements native metadata parsing, immutable transitions and the separate C API; no persistence adapter, pixel operation or renderer is implemented. The test-only oracle remains an engineering specification.

## Audit and acceptance boundary

At the Step 1 audit, core.cpp/core.h exported only pixaura_get_core_info. ABI 1 remains a fixed 16-byte, caller-owned probe: invalid arguments/versions leave output untouched; features and reserved fields are zero. Step 2 adds document.cpp/document_api.cpp and document.h to the same CMake/Android/Swift builds. Independent C/C++ consumers and platform tests validate the boundary. Shell probe calls remain off the UI thread. No import service, filesystem repository, SQLite connection, codec, evaluator or renderer exists.

SavedStateHandle/SceneStorage restore destination and edit mode only. They must never become document history stores. Private managed files, backups excluded, read-only originals, SHA-256 asset identity, SQLite metadata, SDR linear-sRGB CPU authority, platform GPU/codec ownership, bounded work and candidate approval are already accepted decisions. Step 1 adds no dependencies or platform permissions and changes no shell, ABI 1 or build inputs.

Acceptance is a complete, internally consistent schema and lifecycle contract; executable synthetic fixtures for deterministic metadata/history; preserved existing gates; an explicit production implementation test backlog. The user attests Phase 0/1 CI completion at authorization. Historical reports retain their original evidence. Step 1 does not claim independent observation of that final CI run or Apple execution on Windows.

## Domain and identity

| Type | Contract |
| --- | --- |
| ImageDocument | Immutable value: schema version, project ID, document ID, one source descriptor, immutable operation records, immutable approved revisions, current revision ID and redo path. A command returns a new value; failures leave its input untouched. One project has one document in schema 1. |
| SourceAsset | Managed original identified by SHA-256 and encoded byte length, never a writable URI. The owning storage adapter derives assets/sha256/HASH under an already opened private project root. No arbitrary path or external provenance URI is serialized. |
| SourceMetadata | Encoded width/height, EXIF orientation 1..8, codec jpeg/png, alpha flag, source ICC profile asset digest or null. Orientation remains recorded, never baked into original bytes; decode normalizes once before evaluation. Missing profile means the explicit SDR sRGB default. |
| EditOperation | Immutable ID, stable type string, operation version, parameter version, typed parameter object. Editing a parameter creates a new operation ID; existing IDs never change meaning. |
| EditParameters | Registry-defined exact keys and bounded integer values with documented units. Versions own validation and semantics together. No locale strings, NaN, infinity, implicit clamping or arbitrary executable expressions. |
| EditStack | Ordered array of unique operation IDs, evaluated left to right from normalized source. A reference can recur in different revisions but not twice in the same stack. Commuting/reordering operations is never inferred. |
| Revision | Immutable ID, single parent ID or null for the one import root, complete ordered stack, actor import/manual/ai, and nullable plan ID. Every record is approved; transient candidates are separate values. |
| Current pointer | Selected approved revision ID. Undo/redo changes this pointer and redo path atomically, not operation values. |
| Candidate | Detached proposed stack, project/document identity, base revision, session ID and generation. Manual gesture or future AI execution may preview it. Explicit commit/AI approval revalidates session, base and generation. No candidate record is allowed in the persisted revision array. |

IDs are exactly 32 lowercase hexadecimal characters, scoped by (project_id, document_id). They are generated by the application service from OS randomness before a command, not inside replay or serialization. IDs must be unique in each entity namespace; cross-document references are invalid. SHA-256 digests are exactly 64 lowercase hexadecimal characters. IDs are opaque identities, not hashes of JSON or timestamps. The same source content may be physically deduplicated only within a storage ownership policy that never deletes retained references. Multi-document projects need a schema migration.

## Revision transitions

There is one root with parent_id null, actor import, plan_id null and stack []. Revision records are in append/commit order; a parent always occurs earlier, making cycles impossible. Non-root revisions have actor manual or ai; ai requires a plan ID, manual forbids one. An AI record means an already explicitly approved batch, not that a planner may write it. Approval authority remains the application service, not an actor string supplied by an untrusted model.

Commit(expected current revision, expected session generation, new revision ID, full proposed stack, new operation records, actor, optional plan ID) validates everything before publishing. New operation IDs must be fresh; every new record must be referenced by the proposed stack. Reused IDs retain identical contents. The stack can append, replace, remove or explicitly reorder operations. The parent is the current revision. Exactly one new revision is appended; current moves to it; redo becomes empty. One gesture/batch is one undo step. Duplicate/no-op submissions need not create a revision; the application service detects exact unchanged stack and returns unchanged state. No clocks, random values or backend choice enter replay.

Undo: at root, return NO_HISTORY and unchanged state. Otherwise prepend the old current to redo, then set current to its parent. Redo: consume the first redo entry only if its parent is current, then move current there. Explicit checkout of any retained revision clears redo. Redo is a contiguous child path, immediate child first, with no repeats. A new branch clears navigation's redo path but keeps every old revision and operation. There is no automatic garbage collection or implicit pruning. Stale session ID, revision OR generation returns STALE_BASE even when undo has returned to the same revision (ABA protection). The application service generates a fresh 128-bit session ID each open; late jobs/candidates from an earlier open cannot publish to a reopened session. The in-memory session generation increases on every published transition, including undo/redo/checkout; it is not serialized, resets when opening a new session, and is bounded at 9007199254740991 without wrapping. Durable storage uses its own monotonically increasing transaction epoch.

An application session swaps immutable document snapshots only after successful persistence. Failed validation/allocation/save leaves the prior active snapshot and redo intact. In-flight previews retain their snapshot and are invalidated by generation; a completion from a stale candidate cannot publish to the UI. Revision replay uses the stack directly rather than recursively accumulating the parent's stack; this prevents duplicate operations after a parameter replacement.

## Operation envelope and registry

Example:

```json
{"id":"00000000000000000000000000000011","operation_version":1,"parameter_version":1,"parameters":{"milli_ev":1250},"type":"pixaura.exposure"}
```

Type is a stable lowercase ASCII namespace, at most 64 bytes. Registry lookup is exact, case-sensitive and independent of actor/UI labels. Changing a numerical recipe, edge/color semantics or geometry bumps operation_version; changing parameter shape/units bumps parameter_version. A registry supports explicit (type, operation_version, parameter_version) tuples only. It must never reinterpret an old tuple through a new implementation. Backward compatibility retains old evaluators/validators or uses an explicit lossless migration with fixtures; unsupported tuples return UNSUPPORTED_OPERATION. A future migration never overwrites retained historical values or original source. Downgrading or skipping unknown operations is forbidden.

These three version-1 contracts are frozen as metadata examples; **none is a shipping pixel implementation**:

| Type / versions | Exact parameters | Intended semantics |
| --- | --- | --- |
| pixaura.exposure / 1 / 1 | milli_ev: integer -5000..5000 | Signed thousandths of an exposure stop; linear-light RGB multiplier 2^(milli_ev/1000), alpha unchanged; kernel numerical tolerance set before implementation. |
| pixaura.crop / 1 / 1 | x_ppm, y_ppm: 0..999999; width_ppm, height_ppm: 1..1000000; x+width and y+height <=1000000 | Rectangle in millionths of the current normalized input extent after preceding geometry. Convert edges with exact rational arithmetic; pixel rounding/resampling and minimum one-pixel admission must be specified in the geometry implementation step. |
| pixaura.rotate / 1 / 1 | quarter_turns: integer 0..3 | Clockwise multiples of 90 degrees, in normalized input coordinates; zero is allowed; swap extents for odd turns. |

Reserved future type identities: pixaura.contrast, pixaura.highlights, pixaura.shadows, pixaura.whites, pixaura.blacks, pixaura.temperature, pixaura.tint, pixaura.saturation, pixaura.vibrance, pixaura.resize, pixaura.brightness, pixaura.sharpen, pixaura.blur and pixaura.filter. Reservation does not register a valid tuple; all reject until a reviewed parameter/recipe contract exists. Free-angle rotation requires a new tuple, not reinterpretation of quarter_turns. Parameters for those future tools are intentionally not invented before their numerical semantics are defined.

Future masks use immutable content-addressed mask assets, with declared source-space coordinates, dimensions, format, transform and version; their operation envelope requires an explicit parameter-version change. The evaluator maps source-space masks through preceding geometry. Masks do not allow arbitrary paths or introduce history merge edges. AI-generated edits use ordinary registered operations with revision actor/plan provenance, not an opaque pixaura.ai pixel tool. Model/provider/mask provenance belongs to bounded local audit records. Generative editing remains out of MVP.

## Manifest schema 1

The synthetic [fixture](../../tests/fixtures/image-document-v1.json) is a complete valid example. All fields below are required. Unknown fields are rejected at every level in schema 1. Arrays preserve their recorded order; no additional defaults or nullable fields are implied.

| Object | Fields |
| --- | --- |
| Manifest | schema_version: 1; project_id: ID; document_id: ID; source: Source; operations: Operation[]; revisions: Revision[]; current_revision_id: ID; redo: ID[] |
| Source | sha256: digest; byte_length: positive integer <=8589934592; metadata: Metadata |
| Metadata | width,height: integers 1..65535 with product <=268435456; orientation: integer 1..8; codec: jpeg or png; has_alpha: boolean (false for jpeg); icc_sha256: digest or null |
| Operation | id: ID; type: stable type; operation_version,parameter_version: positive uint32; parameters: exact registry-defined object |
| Revision | id: ID; parent_id: ID or null; stack: ID[]; actor: import/manual/ai; plan_id: ID or null |

Metadata dimension/encoded-size ceilings are parser admission limits, not a promise that a device can decode that image. Decoder and job admission additionally use checked dimension/channel/tile arithmetic and the OS-safe tier budget before allocating pixels. This source descriptor must be verified against copied original bytes and decoded metadata by the future import/storage adapter; metadata parsing alone proves neither source existence nor hash integrity. Private EXIF/profile bytes remain in immutable source/profile assets, outside the JSON and logs. Export strips location by default per PHOTO_ENGINE.md.

Boundaries: manifest UTF-8 <=8 MiB; nesting depth <=16 (root is depth 1); all strings <=256 UTF-8 bytes; operations <=4096; revisions 1..4096; each stack <=256; redo <=4095. Duplicate IDs, repeated stack references, cycles, dangling references, unreferenced operations, multiple roots, wrong actor/plan associations and noncontiguous redo paths are invalid. No silently ignored records or partial-document opening. Limits fail RESOURCE_LIMIT without eviction/pruning. Numeric tokens must be plain decimal integers: no exponent, fractional form, leading zeros or negative zero. All integer values lie within signed exact JSON range +/-9007199254740991 and their narrower field bounds. Raw control characters, invalid UTF-8, BOM, unpaired Unicode surrogates, duplicate object keys, trailing input and null where an object is required reject before domain construction. JSON escape-equivalent keys count as duplicates. Production parsing must enforce depth/bytes before recursive descent or allocation amplification; duplicate detection cannot be delegated to an ordinary last-key-wins JSON parser.

Canonical serialization: validate a complete document first; sort object keys by ASCII byte order at every level; preserve arrays; shortest decimal integer form, true/false/null in lowercase; standard JSON escapes for quotes, backslash and controls; other valid Unicode emitted directly as UTF-8; no insignificant whitespace/BOM; exactly one LF terminator. Identity strings/keys/types are ASCII in schema 1. Canonical output must remain <=8 MiB. Parsing can accept noncanonical key order/whitespace but writing normalizes it. Determinism means byte-for-byte equality for identical recorded values/IDs/orders, not identical randomly created project IDs. Hashes for caches are computed over canonical operation/stack bytes and declared assets/versions, not over locale pretty-printing.

Unknown schema returns UNSUPPORTED_SCHEMA. Unknown type/version returns UNSUPPORTED_OPERATION with bounded field/index diagnostics, never source content. A project containing unsupported historical operations is retained byte-for-byte and opened only by a separate non-editing recovery inspector; normal domain loading fails as a whole. No rendering/export or saving over that project is permitted until a compatible registry/migration is available. Malformed/corrupt projects are quarantined read-only with explicit recovery status; never automatically reset to an empty project or delete originals.

## Persistence and crash recovery

SQLite is the live catalog/transaction authority, accessed by platform adapters; the shared C++ contract determines the meaning of records. Store project/document identity and schema version; append-only immutable operation/revision records; current pointer, redo path and commit epoch in the same transaction. Schema 1 manifests are canonical snapshots for checkpoint/interchange. They do not contain filesystem roots, external URIs, pixels, handles, caches, transient candidates or an independently mutable catalog pointer. A live project uses the catalog on reopen; a standalone snapshot is imported as a new validated local catalog with verified managed assets.

Save sequence: validate and budget the candidate; stage any new asset under the owned private root; write fully, flush file, close, atomically rename to its digest path without replacing a mismatched existing object; flush directory where supported; verify existing digest if deduplicating. Only then transactionally insert operations/revision and move current/redo/epoch with compare-and-swap on expected epoch. A crash before the transaction leaves an unreferenced asset, never a broken committed reference. A crash during it restores all or none via SQLite. Publish the in-memory snapshot only after transaction success. No content logging. SQLite durability settings/platform flush guarantees must be documented and fault-injected before adapter promotion, not assumed from an API returning success.

Checkpoint save writes a unique sibling temporary manifest, flushes/closes it, atomically replaces only the checkpoint within the private project root, then flushes the parent where supported. Cross-filesystem rename is forbidden. On unsupported platforms expose a documented recovery protocol retaining the prior valid snapshot rather than asserting atomicity. Checkpoints are derived after catalog commit; an interrupted checkpoint cannot roll back the live catalog. On standalone import, a failed validation/asset check leaves the existing project unchanged.

Recovery validates catalog/schema and all referenced assets, restores current plus redo atomically and rejects missing/hash-mismatched assets. Unreferenced temp/candidate assets can be removed only after ownership/reference reconciliation; retained branch references count as live. No automatic removal of unsupported/malformed project data. Corrupt catalog recovery may explicitly offer a verified checkpoint as a separate recovered project, with the original preserved; never silently treat an old checkpoint as the latest accepted state.

Migration is an explicit, bounded schema-to-schema transform on a temporary copy with backed-up prior metadata, invariant validation and atomic publication. Unknown future schema is read-only unsupported. Old versioned operation records retain their interpretation; recipe upgrades produce a new explicit revision, not changed historical pixels. Catalog storage schema and manifest schema are independently versioned and migration-tested; neither equals ABI/operation version. Full database, migrations, durable import/export and garbage collector are not implemented here.

## C++ domain and C ABI design

C++17 internal domain owns validated values. Strong ID/digest types, bounded parameter variants, immutable SourceAsset/EditOperation/Revision/ImageDocument and a registry separate validation from evaluation. Constructors are private; create/deserialize return Result<T> rather than accepting unchecked field bags. Public-facing immutable values use shared_ptr<const ImageDocument>; a project session holds the active snapshot, generation and persistence adapter. Retained jobs use shared ownership of their snapshot and read-only source capability; destructors release exactly once. No domain value holds a writable source file descriptor or arbitrary path.

Step 1 intended internal interface (design notation, not compiled declarations; Step 2 metadata-only Result interfaces are in document.hpp, and VerifiedSource awaits the import adapter):

```cpp
Result<DocumentSnapshot> create_document(const VerifiedSource&, DocumentIdentity, RevisionId);
Result<DocumentSnapshot> deserialize(ByteView manifest, const OperationRegistry&, Limits);
Result<std::string> serialize(const ImageDocument&, Limits);
Result<DocumentSnapshot> transition(const ImageDocument&, const ValidatedCommand&);
Result<ValidatedStack> validate_stack(const ImageDocument&, const ProposedStack&, Limits);
```

VerifiedSource is issued by the import adapter only after immutable copy/hash/metadata validation. Deserialization yields metadata needing separate asset verification before jobs, not an automatically verified source capability. ProposedStack is a candidate, never approved state. The application service provides trusted approval evidence and checks generation before submitting a commit; the domain checks expected revision and structural invariants. Render validation is const and cannot invoke transition. No renderer API is exported until jobs/tiles exist.

**ABI 1 remains byte-for-byte unchanged**, including zero feature bits. The user-approved Step 2 clarification supersedes the earlier proposed feature-bit advertisement and process-local registry. The document family is additive and independently negotiated at version 1. See accepted [ADR 0009](../adr/0009-explicit-document-context.md); all Step 1 document/history/SQLite/schema decisions remain frozen.

The new C family uses explicit caller-owned context storage: initialize/destroy a registry context; open/create detached metadata with a caller-supplied session identity; apply bounded commands to immutable snapshots; serialize; release. Every handle operation receives the owning context. Manifest input is at most 8 MiB and command input at most 64 KiB, with uint64 lengths checked before size_t conversion. No file, database, rendering or approval capability crosses this API.

Context storage is zero-initialized by the caller and remains accessible through destruction and any repeated-destroy check. It must not be copied or altered. Initialization/destruction require exclusive access and no in-flight calls. Live registry access is synchronized, and acquired immutable snapshot references survive concurrent handle release. The caller supplies a fresh context identity unique across context lifetimes, just as it supplies fresh session identities; reuse is prohibited, including reinitialization at the same storage address. A handle consists of context identity and nonzero monotonically increasing serial, never a pointer address. Serials never wrap or reuse; exhaustion rejects. Cross-context, forged, stale, released and destroyed-context uses reject. Destroy releases all owned handles; a second destroy safely rejects while caller storage remains valid. No singleton or hidden global mutable document state exists. Truthful accessible pointer capacities remain a caller obligation of the C ABI.

Document family 1 uses 64 bytes of caller-owned context storage (version, struct_size, uint64 reserved, 48 opaque ownership bytes) and a 56-byte handle (version, struct_size, uint64 reserved, 32 ASCII identity bytes, uint64 serial). Reserved fields are zero. The context is entirely zero-initialized before init; init writes its version/size. One context admits at most 64 simultaneously owned snapshots; exceeding this runtime ownership budget returns RESOURCE_LIMIT without evicting handles or history. Releasing handles permits new allocations but does not reuse serials. This runtime limit does not change schema-1 document count/byte limits.

Concrete declarations live in `packages/core/include/pixaura/document.h`. Error/status assignments and two-call serialization rules below are unchanged. Only validated immutable document snapshots enter a context registry. Apply returns a detached proposed snapshot; approval, persistence and active-session publication remain application-service responsibilities. Session identity and generation belong to the snapshot's nonserialized concurrency envelope, not the manifest. Commands contain command_version 1, kind, expected_session_id, expected_generation, expected_revision_id, plus the kind's exact payload: commit carries fresh revision_id, full stack, new operations, actor and nullable plan_id; checkout carries revision_id; undo/redo carry no payload. Unsupported command versions return UNSUPPORTED_ABI; unknown kinds return INVALID_ARGUMENT. Stale session, generation or base returns STALE_BASE. Creating an initial document accepts a fully validated root-only manifest; it does not verify source bytes or grant a VerifiedSource capability.

Exceptions including bad_alloc are contained at C entry points and translated to RESOURCE_LIMIT/INTERNAL_ERROR. Open/create/apply produce a newly owned handle only on success; release owns one reference; double release returns INVALID_HANDLE. Handles/session envelopes are not serialized. New snapshots retain all historical records and cannot mutate their inputs. Application transitions and publication are ordered on an application worker queue; core transitions alone do not mark a proposal as durably approved.

Document-family status assignments: 0 OK; 1 INVALID_ARGUMENT; 2 UNSUPPORTED_ABI (document family); 3 INVALID_HANDLE; 4 UNSUPPORTED_SCHEMA; 5 UNSUPPORTED_OPERATION; 6 INVALID_PROJECT; 7 INVALID_PARAMETERS; 8 RESOURCE_LIMIT; 9 STALE_BASE; 10 NO_HISTORY; 11 BUFFER_TOO_SMALL; 12 IO_ERROR; 13 CANCELLED; 14 INTERNAL_ERROR. These are exported new-family values in document.h; existing core.h values 0/1/2 cannot change. Status is int32_t, never a compiler-dependent C enum layout. Error diagnostics contain code, field/index and bounded text, no paths/EXIF/prompts; no global last-error buffer. Input/output pointers and lengths are caller-owned, nonoverlapping, valid for the call only. Core copies validated inputs and retains no borrowed buffer. Null-pointer/length combinations are checked; native callers remain responsible for truthful memory capacity.

The implemented error layout has uint32_t api_version, uint32_t struct_size, int32_t code, uint32_t field_index, uint32_t message_bytes, uint32_t reserved, then uint8_t message[160]; total 184 bytes, alignment 4, message offset 24. Caller initializes api_version=1, struct_size=184 and reserved=0; optional null is valid. Unsupported error layout returns INVALID_ARGUMENT before writing other outputs. Message bytes are bounded ASCII diagnostic identifiers (no NUL required); unused bytes/reserved are zero on a written result. A valid supplied error struct is filled on success or failure; success is code 0, empty message. field_index is an operation/revision array index where relevant, otherwise UINT32_MAX. All other result outputs remain untouched on failure except the explicit serialization required-length rule below. Layout assertions, undersized error buffers and output sentinels are mandatory native tests when this family is introduced.

Serialization is a two-call size-query/fill operation with required length output (includes LF, no NUL). A null buffer with capacity zero queries; a too-small buffer returns BUFFER_TOO_SMALL and writes only required length plus optional validated error, never partial bytes. Other failures leave the byte buffer and required length untouched, while an optional validated error may report the failure. A snapshot is immutable, so the queried length remains valid until release. uint64_t counts and fixed-width statuses cross the ABI; every future struct starts with version/struct_size, with explicit reserved zeros and tested layout. Buffer ownership/release uses one allocator domain; no malloc/free across modules. The document-family functions are now declared in document.h and compiled in every core build. Independent C/C++ and platform tests cover lifetime, layout and fixture parity; Apple execution still requires CI.

## Preview, export and result contracts

PreviewRequest: immutable document snapshot identity, approved revision ID OR detached candidate plus base/session ID/generation, request ID, maximum output extent (720/1280/2048 tier cap), backend preference, explicit SDR display transform, byte/time budget and cancellation token. Requested revision must belong to the snapshot; unknown operation/version rejects. A request never changes current/redo/approval/catalog. Session ID, newest generation and request ID govern UI publication, not completion order. Reduced preview dimensions never alter operations or export resolution.

ExportRequest: explicitly selected approved revision ID and snapshot, new destination capability issued by platform adapter, JPEG/PNG encoding settings, sRGB output policy, location stripping default, requested dimensions and resource budget. Candidate export requires prior approval. Destination capability must be proven disjoint from source/managed asset identities by the platform adapter, including aliases/symlinks, before any write. Core sees a write-only new-output sink and a separate read-only source, not two arbitrary paths. Output is tiled at requested dimensions; no silent resolution downgrade. Reservation/temp/finalization/failure cleanup belongs to the adapter under PHOTO_ENGINE.md.

RenderResult: request ID, snapshot/revision or candidate identity, session ID/generation, state queued/running/succeeded/failed/cancelled; success owns a native surface/tile/result handle plus dimensions/color/alpha metadata; failure owns a typed error and no publishable output. Exactly one terminal state; cancellation acknowledgement does not release resources until workers finish. Resource admission checks overflow and peak buffers before launch; backend fallback uses identical semantics and declared numerical tolerances. Future GPU scheduling operates on the same validated stack and cache keys. No jobs, surfaces, pixel buffers or exports exist in Step 1.

## Safety invariants and implementation test obligations

| Invariant | Required evidence |
| --- | --- |
| Original bytes never overwritten; export disjoint | Real managed synthetic asset SHA-256 before/after edit, undo, preview, export, failure and restart; alias/source-destination rejection; read-only capability tests. Step 1 has no filesystem writer. |
| Past revisions/operations immutable | Golden stacks and serialized historical records unchanged after parameter replacement, branch, stale command and validation failure. |
| Reproducible history and ordering | Fixed-ID canonical fixture, replay returns recorded stacks, replacement does not append ancestor stack twice; identical bytes across Windows/Linux/macOS production implementation. |
| Undo/redo retains branches | Root NO_HISTORY, repeated undo/redo, commit after undo, checkout old branch, reload redo path, stale base and ABA generation. |
| Invalid/future operations fail safely | Exact bounds/types/keys, tuple lookup, invalid crop sums, type/version/schema rejection; no clamp/skip; unchanged prior document. |
| Parsing bounded and validated | Invalid UTF-8, duplicate/escaped keys, corruption/truncation, depth/byte/count limits, dangling/cyclic/cross-document refs, fuzz seeds and production parser ASan/UBSan. |
| Rendering never commits | Request snapshots/pointers unchanged by preview/export success/error/cancel; late completion cannot publish; approved-only export. |
| Ownership/ABI safety | Independent C/C++/Swift/JNI null/length/version tests, handle stale/double-release/forged/concurrent-release tests, output sentinels, exception/allocation injection, 32-bit checked casts and job cancellation lifetime under sanitizers. |
| Durable recovery | Fault injection before/after every asset/catalog/checkpoint flush/rename/transaction; last accepted revision/redo restored; missing/corrupt assets fail read-only; migrations preserve source/history. |

Step 1 test-only oracle validates the metadata fixtures and navigation/validation transitions with no IO/pixels. It is not shipped to Android/iOS and cannot satisfy native parser, numerical replay, source hashing, ownership, persistence or crash-safety gates. All of those obligations remain mandatory as their production paths land. G5 durable persistence and G6 renderer parity are not implemented in Step 1; their absence is explicit scope, not a waived gate. Existing Phase 0/1 gates stay in both workflows. New contract tests run on Windows/Linux/macOS Foundation source jobs and the shell source job.
