# Cooperative cancellation, version 1

The new synchronous working_evaluate_cancel accepts an explicit token from cancel_create in the same decode context. Tokens share fresh context identity/monotonic never-reused serial allocation and the combined 64-handle ceiling, but have a distinct registry/kind. No raw owning pointers, globals or platform thread primitives cross the C ABI. Signal is atomic, sticky and idempotent; no reset. Retry uses a fresh token. Release invalidates future lookup; repeated release/signal after release return invalid handle 3. An admitted in-flight evaluation retains shared ownership until it finishes, even if the handle is released. Release alone does not request cancellation. Context destruction frees remaining tokens and requires all calls to quiesce/join; racing destruction/free is forbidden as in ADR 0009.

Checkpoints: before admission and after acquiring the ordinary context mutex; after bounded parsing and before destination allocation; before each 128x128 tile of input copy/finite validation and each nonzero exposure pass; before each operation; at kernel completion; immediately before handle insertion/publication. Maximum arithmetic between tile checks is 16384 pixels (65536 components); input finite validation and exposure have the same tile bound. Parsing <=64 KiB/256 objects, allocation/value initialization <=128 MiB and mutex acquisition are non-preemptible bounded phases. OS allocator/lock scheduling can delay acknowledgement; no fixed wall-clock latency is promised. No per-pixel atomic polling or unsafe termination.

Cancellation returns existing CANCELLED 13, distinct from invalid input, unsupported operation, resource/allocation limit and internal failure. It publishes no handle/partial raster and preserves caller output, immutable source/history and context validity. Private buffers and shared token references release on every failure. Subsequent valid requests work. A fresh token permits retry against the same immutable source; historical revisions never change.

Cancellation signal and final publication serialize using the separate signal mutex. If signal wins before final check, return 13 with output unchanged. If publication wins, success remains valid and a later signal affects subsequent uses of that token, not the completed result. Invalid API/argument/token checks may precede cancellation; cancellation is not permission to bypass handle safety. A sticky token is checked before parsing/source lookup after structural call/token validation. Existing evaluate has no token and retains its API/semantic behavior, now with deterministic tiled scalar traversal.

Ordinary same-context image calls serialize, including read-only copies and independent evaluations. Signal/release bypass that ordinary mutex and may run from another thread; token creation uses the ordinary mutex. Independent contexts execute concurrently. No internal parallelism, hidden pools or scheduler. Caller keeps context storage, borrowed request/limits/source/token argument memory valid for the call. Token handles themselves are immutable caller values; do not mutate their storage concurrently. Applications own candidate generation/request checks and UI publication per the historical document contract. Cancellation state is transient and never stored in SQLite.
