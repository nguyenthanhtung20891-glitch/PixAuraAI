# Interactive preview lifecycle, version 1

## Authority and identity

Only a request still current and uncancelled may publish a native preview or replace the application's displayed copy. Completion order and cancellation latency never grant authority. This contract extends Steps 9/10 without changing pixels, editing, document/session generations, persistence or ABI 1. Preview generation is a distinct transient context namespace, not document approval.

An immutable ticket contains version 1, struct size, stable kind PRV1, reserved zero, fresh caller-supplied 32-byte context identity and uint64 generation. Begin increments a context-local counter starting at 1. UINT64_MAX may be issued once; the next begin returns RESOURCE_LIMIT(8), preserving state/output. No wrap, timestamp, pointer or generation reuse. Context identities must remain unique across lifetimes under ADR 0009. Tickets are non-owning values, not registry handles or an authentication boundary against a caller that can mutate arbitrary C memory.

Validate version (2), malformed/cross-context/zero/future/kind identity (3). An issued obsolete, cancelled or stopped ticket loses eligibility with CANCELLED(13). Duplicate cancellation of the current ticket succeeds; cancellation of an older ticket cannot cancel the newer request. Completed requests can be cancelled/superseded to revoke delayed platform installation. A request may enter rendering once; duplicate execution returns 13. Render failure is terminal for that ticket; retry begins a fresh generation.

## Native lifecycle and fence

Idle -> begin/current -> claim rendering -> validate/admit -> private result -> fence -> owned native handle -> bounded platform copy -> explicit native release. Begin can supersede an in-flight render without waiting for the ordinary context mutex. Under the existing cancellation mutex it advances current generation (immediate authority revocation) and resets only the new generation's cancellation flag. Old renders use a stack-only view of the same atomic generation/revocation state at existing cooperative checkpoints.

The ordinary context mutex serializes source lookup, resource admission, conversion and registry insertion; source release waits on it, so an admitted source cannot be freed during access. Release that wins before admission returns stale handle 3. Before publication the cancellation mutex proves current generation, no explicit cancel/stop and retained context validity; insertion and caller output assignment occur under that fence. Resource accounting cannot change while the ordinary mutex is held. Each interactive preview registry entry records its producing generation. Current(context,ticket,optional preview) checks eligibility and, when supplied, actual result kind/generation binding. It never consumes a handle.

Signal/advance/check without a result use only the small cancellation mutex. No worker, scheduler, callback executor or thread pool. Independent contexts remain independent. Existing exact/fit preview and cancellation-token APIs retain their behavior.

Explicit cancel and stop revoke eligibility and use the same checkpoint status 13. Stop is idempotent and prevents further interactive begin. Destruction protocol: stop -> join/quiesce all native calls -> existing context destroy. Native destroy does not race/free active storage or implicitly spawn/wait for workers. Platform adapters implement the join before destroying. Context storage remains accessible until all calls complete; previously detached platform copies survive close.

## Platform publication and replacement

Android InteractivePreview and Apple InteractivePreview own all begin/cancel/stop and install transitions for their native context. One short-held platform lock covers native eligibility check AND displayed-reference replacement; begin/cancel cannot enter the gap. Rendering and platform copying run outside this lock, off the UI thread. Raw native lifecycle mutations must not bypass the owner: a check followed by an unsynchronized UI assignment is insufficient.

Candidates carry immutable context identity bytes and generation, never owner pointers or strong references to native contexts. Constructors are restricted; stale or cross-owner candidates cannot install. Native handles are released after copying, independently of display. Installation uses native current eligibility under the owner lock. Retain only latest requested ticket and last successfully displayed candidate; failure/cancel never blanks the old display. Older displayed images may stay visible after a failed newest request but cannot be newly installed once superseded. Replacement drops only the owner's reference; externally held Bitmap/CGImage copies remain valid. No automatic Bitmap recycling while another owner may draw it.

Android privately owns a fixed direct ByteBuffer for context/working-handle/identity storage; it is never copied, exposed, persisted or used as an image buffer. JNI checks capacity/alignment. Generation bits cross JNI as Long without signed ordering; zero alone means begin failed. Close signals stop, waits for active synchronous render/copy calls, then destroys. Swift owns stable context storage and an NSCondition join, offers preparation before the first begin, and never lets native context storage move. Each platform owner admits at most two active render/copy calls; a third returns no candidate without eviction. Retained owner state is one requested ticket and one displayed candidate. Platform copies retain Step 10 <=1024 dimensions, <=4 MiB pixel payload per copy; they are external app-owned allocations, not a native cache.

## Bounds, cancellation and failure

Fixed native lifecycle control: one uint64 atomic counter, one bool atomic revoked flag and two bool flags (plus implementation padding, at most 32 bytes of fields). Each live render uses a bounded stack Cancellation view; no request map, historical ticket retention or request-control allocation. A preview entry adds one uint64 producing generation; <=64 entries. Existing Cancellation objects add bounded internal view fields; <=64 shared token handles. Fixed registry/object overhead remains additional under ADR 0011 and is not raster payload or a peak RSS claim. Retained raster/vector capacities, provenance and payload reservations continue to count fully. 128 MiB/8388608 pixels/256 MiB/64 handles unchanged; no eviction, cache or increased ceiling.

Fit checks every 1024 source/destination pixels and before each lazy 128x128 destination tile; exact preserves Step 9 tile checks (<=16384 pixels). Admission, allocation and publication checks remain. Largest non-preemptible phases include bounded source layout, allocation/value initialization of <=32 MiB preview bytes, lock acquisition and registry allocation/OS scheduling. No hard real-time latency claim. A missed/delayed cooperative check cannot defeat the final generation fence.

Argument/source/request/layout/resource/allocation/numeric/cancellation/registration failure leaves caller outputs and existing handles/history/source unchanged and reclaims private pixels. Earlier platform copies stay valid. A failed newest generation remains newest requested until another begin; it does not promote an older result. Existing statuses only. Fixed metadata has no allocation site; interactive render sweeps exercise destination object/buffer and registry publication failures with fresh-generation recovery.

## Verification

Required tests: C ABI and JNI/Swift consumers; 10000-request bounded churn; fixed-seed malformed identities; every observable conversion checkpoint supersession and explicit cancellation; final publication races; source release and stop/join; overflow without wrap; same-context cap/aggregate rejection, repeated release recovery and no historical registry growth; delayed platform copy/install rejection and failed-request display preservation. Existing exact/fit numerical oracle tests, sanitizers and all local/hosted platform gates remain mandatory. Diagnostics report churn/control timing only, not device frame latency.
